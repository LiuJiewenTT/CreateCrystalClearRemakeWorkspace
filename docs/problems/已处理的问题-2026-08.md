## 13. illumination 包覆齿轮侧面贴图路径不一致

**日期**：2026-08-25

**问题描述**：`GlassBlockBuilders.java` 中 `getIlluminationSiding()`（第 394-397 行）和 `getIlluminationCogCTBehaviour()`（第 351-356 行）引用 `{material}_illumination_encased_cogwheel_side` 贴图路径，但所有 32 个 illumination 齿轮模型 JSON 手写引用的是 `{material}_encased_cogwheel_side`（不带 illumination），两者路径不匹配。导致 illumination 齿轮的 CT 连接效果实际未生效。若未来启用 datagen，代码生成路径会引用不存在的贴图。

**修复方案**：采用独立路径方案（路线 B），为未来侧透版机壳预留独立贴图通道：

1. 创建 12 个 illumination 专用 siding 贴图（4 材质 × 3 形态），初始内容复制自对应普通版：
   - `{material}_illumination_encased_cogwheel_side.png`（4 个，small）
   - `{material}_illumination_encased_cogwheel_side_connected.png`（4 个，CT 精灵表）
   - `large_{material}_illumination_encased_cogwheel_side.png`（4 个，large）
2. 修改 32 个 illumination 齿轮模型 JSON 的 siding 引用为 illumination 专用路径
3. 代码无需修改（`getIlluminationSiding()` 和 `getIlluminationCogCTBehaviour()` 原有路径即正确）

独立路径方案使资源包可分别替换普通版和照明版的侧面贴图，为未来添加侧透版机壳预留了通道。

## 15. 开发环境配置 GUI 集成与 JEI 版本升级

**日期**：2026-08-25

**问题描述**：配置功能（#14）代码实现完毕并编译通过，但开发者在 runClient 测试时缺少游戏内配置 GUI——无法通过 Mods 页面点击 Config 编辑配置项来验证配置功能是否正常工作。需要引入第三方 mod 作为开发环境运行时依赖，提供配置界面用于测试。此依赖仅用于开发环境，不会打包到发布版本，最终用户不受影响。

**方案调研与选型**：

1. **Better ModList**：最初尝试，但 javap 反编译确认从最早版本 1.0.2 到最新 21.1.1 全部带有 `@SubscribeEvent` 注册到公共事件总线的 bug（`RegisterKeyMappingsEvent` 是 Mod Bus 事件，NeoForge 21.1.152 拒绝此做法），所有版本不可用。

3. **Configured（MrCrayfish）**：首先适配。CurseForge 上的配置 GUI mod，自动为所有注册了 `ModConfigSpec` 的 mod 生成交互式配置界面。作为 `localRuntime` 依赖引入，仅在开发环境 runClient 时加载，不参与编译产物。

## 16. NeoForge 内置配置界面适配

**日期**：2026-08-26

**问题描述**：配置功能（#14）在 #15 中通过 Configured mod 适配了开发环境配置 GUI。在此基础上，继续适配 NeoForge 1.21.1 自带的 `ConfigurationScreen` 交互式配置 GUI——通过注册 `IConfigScreenFactory` 扩展点即可使用，无需任何额外依赖。两种方案并行存在，作为不同的适配路径。

适配过程中发现 NeoForge 内置 `ConfigurationScreen` 有自己的翻译键体系，通过 `TranslationChecker` 在开发环境下检查翻译键缺失并输出 WARN 日志。通过反编译 `ConfigurationScreen$TranslationChecker` 和 `ConfigurationScreen` 字节码确认了 4 个翻译键的生成规则。

**修复**：

1. **实现**：
   - `build.gradle` 中注释掉 `localRuntime name: 'configured-neoforge-1.21.1-2.6.1'`（jar 和 gradle.properties 版本号保留）
   - `CrystalClear.java` 注册 `IConfigScreenFactory` 扩展点：
     ```java
     modContainer.registerExtensionPoint(IConfigScreenFactory.class,
         (mc, parent) -> new ConfigurationScreen(modContainer, parent));
     ```

2. **翻译键决定不添加**：TranslationChecker 对这 4 个键使用 `check(key, fallback)` 带回退机制，缺失时自动回退到默认值（如标题用 mod 显示名、分区名用配置文件名），默认效果已足够好。这些键属于可选的个性化扩展，当前无定制需求，不添加。开发环境 runClient 时打开配置界面仍会看到 TranslationChecker WARN 日志，这是预期行为。

   翻译键生成规则记录在知识文档中（作为 NeoForge 开发知识备查），但本项目不添加这些翻译键。

3. **知识文档更新**：`docs/knowledge/NeoForge配置GUI翻译机制.md` 补充了 NeoForge 内置 ConfigurationScreen 的翻译键生成规则、TranslationChecker 行为说明、以及与 Configured 的对比总结。

**编译验证**：BUILD SUCCESSFUL
