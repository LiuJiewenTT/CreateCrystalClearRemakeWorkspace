# 文档层级结构

> 本文档说明 `docs/` 目录下各类文档的层级关系和组织规则。

## 一、三层核心结构

文档按"从计划到进展到具体问题"的逻辑分为三层，层层展开，一层比一层详细：

```
第一层：工作计划层（做什么）
  ├─ 工作计划.md（当前活跃阶段）
  └─ 工作计划-存档-阶段X-XXX.md（已完成阶段，每阶段独立存档）
      ↓ 对应
第二层：progress 层（做了什么）
  └─ progress/阶段X-XXX.md（每阶段一份区别报告 / 探索报告）
      ↓ 对应
第三层：problems 层（遇到什么问题）
  └─ problems/已处理的问题-YYYY-MM.md（按月汇总，跨阶段连续编号）
```

### 各层职责

| 层级 | 文件位置 | 内容 | 粒度 |
|------|----------|------|------|
| 工作计划层 | `docs/` 根目录 | 阶段目标、任务清单（带复选框）、实施范围、不处理项 | 最粗：只列"做什么" |
| progress 层 | `docs/progress/` | 变更详情、源码分析、方案对比、编译验证结果、commit 记录 | 中等：说明"怎么做的" |
| problems 层 | `docs/problems/` | 具体问题的现象、原因、修复方案、涉及文件 | 最细：记录"遇到什么问题、怎么修的" |

### 按阶段对应关系

| 阶段 | 计划层文件 | progress 文件 | problems 编号范围 |
|------|-----------|---------------|-------------------|
| 验证阶段 | `工作计划-存档-验证阶段.md` | `原始项目-vs-Adonis重构项目.md`（对照分析，非标准区别报告） | #1 ~ #4 |
| 阶段四 | `工作计划-存档-阶段四-重建重构.md` | `重建重构阶段.md`（第一~五节） | #5 ~ #8 |
| 阶段五 | `工作计划-存档-阶段五-功能迁移与完善.md` | `重建重构阶段.md`（第六~十六节）* | #9 ~ #17 |
| 阶段六 | `工作计划.md`（活跃） | `铜透明包覆水管特性是否存在的前期探索.md` + `阶段六可行性探索-玻璃机壳包覆铜水管.md` | 待产生 |

> *\* 已知结构问题：阶段五的进度报告追加到了阶段四报告文件 `重建重构阶段.md` 中，未独立成文件。后续可考虑拆分。*

## 二、辅助文档

除三层核心结构外，还有以下辅助文档：

| 目录 | 文件命名规则 | 用途 |
|------|-------------|------|
| `potential_problems/` | `潜在问题.md` | 记录发现的隐患或待定问题，与 problems 层互补（problems 是已处理的，这里是不确定要不要处理的） |
| `knowledge/` | 按主题命名 | mod 开发教学知识点，概念讲解和使用指南 |
| `manners/` | `规范.md` | 工作流程、编码规范、操作准则 |
| `future/` | `未来参考选用事项-YYYY.md` / `无计划意图的事项-YYYY.md` | 未来可能考虑做 / 明确不做的事项 |
| `help_wanted/` | `求助事项.md` | 希望寻求外部帮助的事项 |
| `changelogs/` | `player-changelog.md` / `developer-changelog.md` | 变更日志，玩家向和开发者向各一份 |

## 三、文档编号规则

- **工作计划层**：任务编号各阶段独立，每个阶段从 1 开始（存档文件同理）
- **problems 层**：跨阶段连续编号，按月文件汇总（如 `已处理的问题-2026-08.md` 包含 #1 ~ #17）
- **potential_problems 层**：独立编号，与 problems 层有交叉引用（潜在问题修复后标记状态，同时在 problems 层记录处理详情）
- **help_wanted 层**：独立编号

## 四、引用规则

- 同目录文件用文件名直接引用：`[文本](文件名.md)`
- 跨目录文件用相对路径：`[文本](../目录名/文件名.md)`
- `docs/` 根目录下的文件引用子目录文件：`[文本](子目录名/文件名.md)`
- problems / changelogs 等文档内部通过 # 编号交叉引用（如"潜在问题 #10"），不需要链接

## 五、AIGC 水印处理

AI 写入的 `.md` / `.txt` / `.json` 等文件会被注入零宽字符水印。处理流程：

1. AI 用 Write/Edit 工具写入文件后，将文件路径加入去水印脚本（`.temp/clean_watermarks_XXXX.ps1`）
2. 提示用户手动执行去水印脚本
3. 用户执行后文档可提交 git
4. 文档不直接提交 git（水印未去除前），若用户允许，代码可正常提交
