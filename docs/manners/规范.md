# 规范

## 工作流程

1. 读取 `文档编写指导.md` 和 `工作计划.md`，读取必要的相关文档，然后向用户确认计划，然后开始工作。
2. 更新计划文档（旧计划转存存档，不删除），然后才开始执行。
3. 执行完成后更新文档（已处理问题记录到 `docs/problems/`，隐患/待定问题记录到 `docs/potential-problems/`）。
4. 每次用 Write/Edit 工具写文档后，调用去水印技能，提示用户手动执行去水印命令。
5. 去水印完成后，再问用户是否继续后续工作。
6. 每 10 次对话温习一遍 README。

## 文件操作

- 文件内容写入使用 Read/Edit/Write 工具，不使用 PowerShell（避免编码问题）。
- 文件/目录移动使用 PowerShell（只移动，不修改内容）。
- 内容修改与移动分开执行，不混在一起。
- 不做删除操作，能保留的尽量保留。如果确实需要删除，必须先问用户，不自作主张。

## Git 友好的移动改名流程

当需要大规模移动/改名文件并修改内容时，必须分开提交以保持 git 历史清晰：

1. 先提示用户是否有想先手动提交的内容
2. 用 `git mv` 执行移动/改名（只移动，不修改内容）
3. stage 并提交（此时 git 识别为 R100 纯 rename，0 insertions / 0 deletions）
4. 然后再编辑内容（包名引用替换、功能补全等）
5. 再提交内容修改
6. commit message 使用复选框语法（`- [x]` / `- [ ]`）标记各项子任务的完成状态

这样 git 历史里两个 commit 分别清晰可见：一个是纯移动，一个是内容修改。如果内容修改中混合了不同类型的改动（如改名 vs 功能补全），也应进一步拆分为独立 commit。

## 功能判断

- 不要仅凭文件名或"零引用"就判断文件无关。old_copper 贴图经对比确认是与正常 copper 贴图有实际像素差异的独立贴图（旧版铜色调 vs 新版铜色调），不应删除。
- 不了解游戏体验逻辑时，不要自作主张做删除或修改决策，应向用户确认。

## 许可与参考

- 注意许可问题，避免直接使用不兼容 MIT 协议的代码。
- 参考原始项目（c0nnor263 修复版，ARR 协议）进行功能比对和查错，但不复制其代码。
- 功能完整性应参考原始项目，不能只改名字不做功能检查。

## 文档隐私

- 编写文档时注意隐私问题，不包含本机绝对路径等隐私信息。
- 本机非普适性问题写入 `-personal` 后缀文档。

## 概念区分

- "工作区"指 `CreateCrystalClearRemakeWorkspace`，不是子模块 `repo/Create-Crystal-Clear`。
- 温习 README 指的是工作区的 README，不是子模块的。
