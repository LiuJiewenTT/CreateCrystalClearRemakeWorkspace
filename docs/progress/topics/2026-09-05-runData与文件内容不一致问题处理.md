# 专题：runData 与文件内容不一致问题处理

> 日期：2026-09-05
> 阶段：阶段六（玻璃机壳包覆铜水管）期间
> 状态：C/F/D/E 类已修复，H 类待处理

## 一、背景

阶段六开发完成后，需将 runData 生成的资源从 `src/generated/resources/` 同步到 `src/main/resources/`。同步前对两个目录进行逐文件比对，发现 56 个同名文件存在内容差异。经分析，这些差异并非全部是"生成器正确、手写过时"，而是混合了多种性质的问题。

本专题将所有差异分类、归档，作为独立的技术参考资料。

## 二、核心发现：Gradle 编译缓存掩盖了 runData 崩溃

此前 runData 一直"成功"是因为 `compileJava UP-TO-DATE` / `FROM-CACHE`，实际使用的是旧 class 文件。强制 `--rerun-tasks` 重编译后才暴露 C 类和 F 类的模型缺失崩溃。

**结论：后续执行 runData 验证时必须用 `--rerun-tasks` 参数，否则编译缓存会掩盖代码中的实际错误。**

## 三、差异分类总览

排除 pipe 新增的 12 个条目后，299 个同名文件中 56 个有差异，分为 8 类：

| 类别 | 文件数 | 根因简述 | 处理状态 |
|------|--------|----------|----------|
| A 换行符 | 11 | CRLF vs LF | 无所谓，不需处理 |
| B replace + 排序 | 3 | main 手动加了 `"replace": false` | main 更好，保持不动 |
| C illumination shaft parent | 8 | 代码引用不存在的 `illumination_encased_shaft/block` | 已修复 |
| D 小齿轮纹理槽 | 12 | gen 用 `1`/`1_2`/`side`，main 用 `backing`/`cogwheel`/`siding` | 已修复 |
| E 大齿轮纹理槽 | 12 | gen 用 `4`，main 用 `large_cogwheel` | 已修复 |
| F 脚手架 parent + top | 6 | 代码引用不存在的 `scaffold/item` + top 纹理不一致 | 已修复 |
| G en_us.json | 1 | main 有手工条目（itemGroup + config） | main 正确，保持不动 |
| H pickaxe.json | 1 | main 缺 40 个条目 | 待处理：补回 28 个非 pipe 条目 |

## 四、各类详情

### A 类：换行符差异（11 个文件）

**文件**：部分 loot table 和 tag JSON 文件。

**差异**：仅 CRLF vs LF 换行符差异，内容完全相同。

**处理**：无所谓，不需要处理。

### B 类：replace 标记 + 数组排序差异（3 个 tag 文件）

**文件**：3 个 tag JSON 文件。

**差异**：main 中手动加了 `"replace": false`，防止本模组的 tag 覆盖原版 Create 的同名 tag。gen 没有 `replace` 字段（默认为 false，行为相同但显式声明更安全）。gen 的 values 数组排序也与 main 略有不同。

**处理**：main 版本更好（显式 `replace: false` 更安全），保持 main 不动。

### C 类：illumination shaft 模型 parent 引用不存在（8 个文件）

**文件**：4 个 block 模型 + 4 个 item 模型（`{casing}_illumination_encased_shaft.json`）。

**差异**：gen 中 parent 指向 `block/illumination_encased_shaft/block`（和 `/item`），但 `src/main/resources` 中不存在 `illumination_encased_shaft/` 目录（只有 `glass_encased_shaft/`）。

**根因**：`GlassBlockBuilders.java` 的 `illuminationEncasedShaft()` 代码引用了 `illumination_encased_shaft/block` 作为父模型，但该模型文件从未创建。此前因编译缓存未真正重编译而未暴露，强制 `--rerun-tasks` 后 runData 崩溃。

**修复**：改代码复用 `glass_encased_shaft/block` 和 `glass_encased_shaft/item`（结构相同，仅 casing 贴图不同）。从 gen 同步 8 个模型到 main（parent 已指向 glass_encased_shaft）。代码中添加注释说明暂无独立模型计划。

**详见**：`docs/problems/topics/已处理问题-2026-09-05-runData与文件内容不一致问题处理.md` 第 C-1 条。

### D 类：小齿轮 item 纹理槽命名（12 个文件）

**文件**：12 个小齿轮 item 模型（`{casing}_{glass/clear_glass/illumination}_encased_cogwheel.json`）。

**差异**：gen 用 `1`/`1_2`/`side` 纹理槽名（Create 原版命名），main 用 `backing`/`cogwheel`/`siding`（本项目自定义命名）。此前 main 手动改过 JSON 但未改代码，导致 gen 仍用旧名。

**根因**：item 模型父模型（`encased_cogwheel/item.json`）的纹理槽命名与 Create 原版不一致。Datagen 代码写入了自定义名称（`backing`/`cogwheel`/`siding`），但 item 父模型此前未更新，导致 gen 产物纹理槽名称不匹配。

**修复**：在上一轮已修改 item 父模型（`encased_cogwheel/item.json`），统一纹理槽命名为 `casing`/`backing`/`cogwheel`/`siding`/`opening`。本轮 runData --rerun-tasks 验证通过，gen 产物与 main 一致。

**详见**：`docs/problems/topics/已处理问题-2026-09-05-runData与文件内容不一致问题处理.md` 第 D-1 条。

### E 类：大齿轮 item 纹理槽命名（12 个文件）

**文件**：12 个大齿轮 item 模型（`{casing}_{glass/clear_glass/illumination}_encased_large_cogwheel.json`）。

**差异**：gen 用 `4` 纹理槽名（Create 原版），main 用 `large_cogwheel`（本项目自定义）。根因同 D 类。

**修复**：已修改 item 父模型（`encased_large_cogwheel/item.json`），统一纹理槽命名。runData 验证通过。

**详见**：`docs/problems/topics/已处理问题-2026-09-05-runData与文件内容不一致问题处理.md` 第 E-1 条。

### F 类：scaffold item 模型 parent 引用不存在 + top 纹理不一致（6 个文件）

**文件**：6 个 scaffolding item 模型。

**差异**：
1. gen 中 parent 指向 `block/scaffold/item`，但 `src/main/resources` 中不存在 `scaffold/item.json`（只有 `scaffold/block.json` 和 `scaffold/block_horizontal.json`）。
2. gen 的 top 纹理用 `getTopTexture(casing)`（返回 `create:block/funnel/{casing}_funnel_frame`），main 手动改为 `{casing}_glass_casing`。

**根因**：`GlassBlockBuilders.java` 的 `glassScaffolding()` 代码引用了 `scaffold/item` 作为 item model parent，但该文件从未创建。同样被编译缓存掩盖，强制重编译后 runData 崩溃。top 纹理方面，代码用原版 Create 的 funnel_frame 纹理（有镂空效果），main 手动改为 glass_casing（封闭玻璃面），两者外观差异明显。

**修复**：
1. parent 改为 `block/scaffold/block`
2. top 纹理改为 `{casing}_glass_casing`（与 main 的手动修正一致）
3. 代码中添加 TODO 注释记录原始纹理和未来设计方向

**详见**：`docs/problems/topics/已处理问题-2026-09-05-runData与文件内容不一致问题处理.md` 第 F-1 条。

### G 类：en_us.json 手工条目（1 个文件）

**文件**：`src/main/resources/assets/crystal_clear/lang/en_us.json`（gen 对应路径不含手工条目）。

**差异**：main 版本包含手工添加的 itemGroup 和 config 相关翻译条目，这些条目不经过 datagen 生成，gen 版本中缺失。如果直接用 gen 覆盖 main 会丢失这些条目。

**处理**：main 正确，保持不动。未来 runData 同步时注意不要覆盖。

### H 类：pickaxe.json 缺失条目（1 个文件）

**文件**：`src/main/resources/data/minecraft/tags/block/mineable/pickaxe.json`。

**差异**：gen 版本有 55 个条目（完整），main 版本只有 18 个条目。main 缺失 37 个条目，其中：
- 12 个 pipe 条目（阶段六新增，本次新增，合理）
- 4 个 illumination_encased_shaft
- 8 个 cogwheel（glass + clear_glass）
- 4 个 illumination_encased_cogwheel
- 8 个 large_cogwheel（glass + clear_glass）
- 4 个 illumination_encased_large_cogwheel

即除 pipe 的 12 条外，还有 28 个非 pipe 条目是 main 历史遗漏的。

**处理**：待处理。需从 gen 补回 28 个非 pipe 条目到 main。pipe 的 12 条已通过其他途径（手写 JSON）存在或处理。

## 五、纹理由来与设计说明

### 纹理槽命名规则（D/E 类）

| 纹理含义 | block 系列模型 | item 父模型（小齿轮） | item 父模型（大齿轮） |
|----------|---------------|----------------------|----------------------|
| 机壳面 | `casing` | `casing` | `casing` |
| 木盘背面 | `backing` | `backing` | `backing` |
| 齿轮侧面 | `siding` | `siding` | `siding` |
| 齿轮本体 | — (渲染器绘制) | `cogwheel` | `large_cogwheel` |
| 开口面 | `opening` | `opening`（默认值） | `opening`（默认值） |

所有 24 个子 item 模型统一提供 `backing`/`casing`/`opening`/`siding`。

### Blockbench 预览问题

Blockbench "打开父级并应用纹理"功能不生效是 BB 自身 bug。item 父模型保留默认纹理值是合理设计（方便直接打开父模型编辑），游戏内 Minecraft 模型解析子模型覆盖父模型默认值，行为正确。两个 item 父模型维持现状，不做修改。
