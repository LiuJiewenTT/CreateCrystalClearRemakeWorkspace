## 八、Copper 系列贴图补全

### 8.1 背景

Copper 材质的包覆轴/齿轮引用了 4 个缺失贴图：`copper_gearbox`、`copper_encased_cogwheel_side`、`large_copper_encased_cogwheel_side`、`copper_encased_cogwheel_side_connected`。Create 6.0.6 jar 中也没有 `copper_gearbox`（只有 `gearbox` 和 `brass_gearbox`），这是原作者 Adonis 添加 copper 扩展时遗留的未完成工作。

### 8.2 方案演进

| 版本 | 方案 | 结果 |
|------|------|------|
| V1 | HSV 色相旋转（brass→copper） | 与原版风格割裂，已撤销 |
| V3 | 直接调色板映射 | 颜色变平，无高光阴影层次，已撤销 |
| V4 | 以 copper_casing 为底图叠加 brass 结构特征（脚本生成） | 结构正确但用户不满意 |
| 最终 | 用户以 copper_casing 为底图手绘 | 满意，已提交 |

关键教训：brass 贴图的高光/阴影是按黄铜色调设计的，颜色替换后层次感丢失。必须以 copper_casing 为底图，保留铜色高光/阴影/铆钉，参考 brass 结构特征叠加。

### 8.3 修改内容

1. **36 个 model JSON 引用路径修改**（commit `7734865`）：`create:block/copper_gearbox` → `crystal_clear:block/copper_gearbox`（models/block/ 27 个 + models/item/ 9 个）
2. **4 个贴图手绘补全**（commit `30a8e7c` + 用户后续提交）：
   - `textures/block/copper_gearbox.png` — 以 copper_casing 为底图，叠加 brass_gearbox 的暗环+中心黑洞结构
   - `textures/block/encased_cogwheels/copper_encased_cogwheel_side.png` — 以 copper_casing 为底图，中间设透明带（齿轮槽）
   - `textures/block/encased_cogwheels/large_copper_encased_cogwheel_side.png` — 铜色框架+灰色面板，水平条纹结构
   - `textures/block/encased_cogwheels/copper_encased_cogwheel_side_connected.png` — 32x32 四象限 CT 精灵表，用于小齿轮侧面连接贴图

完成全量扫描：模型 JSON 层（195 个文件）、blockstates 层（348 个引用）均无断链。确认铜系列缺失的 4 个贴图已全部由用户手绘补全。

## 九、代码-资源一致性修复（5.5：潜在问题 #6 #9）

### 9.1 背景

在 5.4 贴图补全排查中发现两处代码与手写 JSON 不一致（潜在问题 #6 #9），均不影响当前运行（手写 JSON 优先于代码生成），但若未来启用 datagen 重新生成资源会产生问题。本阶段对此进行修复。

### 9.2 #6：大齿轮 blockFolder 路径不一致

**问题**：`GlassBlockBuilders.java` 中大齿轮 builder 代码设置 `blockFolder = large ? "encased_large_cogwheel" : "encased_cogwheel"`，但资源目录中只有 `encased_cogwheel/`，`encased_large_cogwheel/` 从未存在。经分析确认大小齿轮共用同一套父模型，3D 几何完全一致，区别仅在于 siding 贴图。

**修复**：将 4 处 `blockFolder` 分叉代码统一改为 `"encased_cogwheel"`，保留注释说明大小区别仅在 siding 贴图。代码修改已提交（commit `edef295`）。

**修改文件**：`GlassBlockBuilders.java`（第 199、213、263、277 行附近，共 4 处）

### 9.3 #9：illumination 侧面贴图路径不一致

**问题**：代码 `getIlluminationSiding()` 和 `getIlluminationCogCTBehaviour()` 引用 `{material}_illumination_encased_cogwheel_side` 贴图路径，但 32 个 illumination 齿轮模型 JSON 手写引用的是不带 illumination 的普通版路径，两者不匹配导致 illumination 齿轮 CT 连接效果未生效。

**修复方案**：采用独立路径方案（路线 B），为未来侧透版机壳预留独立贴图通道：

1. 创建 12 个 illumination 专用 siding 贴图（4 材质 × 3 形态），初始内容复制自对应普通版：
   - `{material}_illumination_encased_cogwheel_side.png`（4 个，small）
   - `{material}_illumination_encased_cogwheel_side_connected.png`（4 个，32x32 CT 精灵表）
   - `large_{material}_illumination_encased_cogwheel_side.png`（4 个，large）
2. 修改 32 个 illumination 齿轮模型 JSON 的 siding 引用为 illumination 专用路径
3. 代码无需修改（原有路径即正确）

独立路径方案使资源包可分别替换普通版和照明版的侧面贴图，为未来添加侧透版机壳预留了通道。

### 11.2 方案选型

| 方案 | 结果 | 原因 |
|------|------|------|
| Better ModList | ❌ 不可用 | 所有版本（1.0.2~21.1.1）均将 `RegisterKeyMappingsEvent`（Mod Bus 事件）用 `@SubscribeEvent` 注册到公共事件总线，NeoForge 21.1.152 拒绝此做法 |
| NeoForge 内置 ConfigurationScreen | 后续适配（#16） | 需在代码中注册 `IConfigScreenFactory` 扩展点 |
| Configured（MrCrayfish） | ✅ 首先适配 | 自动为所有注册了 `ModConfigSpec` 的 mod 生成交互式 GUI |

### 11.4 JEI 版本升级

Configured 2.6.1 的 `neoforge.mods.toml` 声明 JEI 依赖 `versionRange = "[19.24.0.317,)"`（optional，但有版本范围检查）。项目原用 JEI 19.21.0.247 不满足，导致 runClient 崩溃。

从 JEI Maven 元数据确认可用版本范围后，选择 `19.24.0.317`（刚好满足要求的最小版本）：

| 项目 | 旧值 | 新值 |

## 十二、NeoForge 内置配置界面适配（5.6 续）

### 12.1 背景

配置功能（第十、十一节）在 #15 中通过 Configured mod 适配了开发环境配置 GUI。在此基础上，继续适配 NeoForge 1.21.1 自带的 `ConfigurationScreen` 交互式配置 GUI——通过注册 `IConfigScreenFactory` 扩展点即可使用，无需任何额外依赖。两种方案并行存在，作为不同的适配路径。

### 12.2 两种适配方案对比

| 项目 | Configured 方案（#15） | NeoForge 内置方案（#16） |
|------|------------------------|--------------------------|
| 依赖 | `localRuntime` Configured jar | 无额外依赖 |
| 注册方式 | Configured 自动发现 | `IConfigScreenFactory` 扩展点 |
| 代码修改 | 无 | CrystalClear.java +1 行注册 |
| JEI 版本 | 需升级到 19.24.0.317 | 不需要（已升级的版本保留） |
| 配置界面翻译 | Configured 自有 `.tooltip` 约定 | NeoForge 自有 4 键体系 |

适配操作：
- `build.gradle` 注释掉 `localRuntime name: 'configured-neoforge-1.21.1-2.6.1'`
- `CrystalClear.java` 新增 `IConfigScreenFactory` 注册（2 个 import + 1 行代码）
- Configured jar 和 `gradle.properties` 中的版本号保留（备用）

### 12.3 翻译键调研与决定

适配后 runClient 验证发现 NeoForge 内置 `ConfigurationScreen` 的 `TranslationChecker` 报告 4 个翻译键缺失。通过反编译 `ConfigurationScreen$TranslationChecker` 和 `ConfigurationScreen` 字节码，确认了翻译键生成规则。

但进一步分析发现：TranslationChecker 对这 4 个键使用 `check(key, fallback)` 带回退机制，缺失时自动回退到默认值（如标题用 mod 显示名、分区名用配置文件名），默认效果已足够好。这些键属于可选的个性化扩展，当前无定制需求，**决定不添加**。开发环境 runClient 时打开配置界面仍会看到 TranslationChecker WARN 日志，这是预期行为。

翻译键生成规则记录在知识文档中作为 NeoForge 开发知识备查。
